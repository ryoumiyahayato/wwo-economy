# 实体经济数量实验：200 日实际运行报告

本实验使用 Python 3 标准库，在独立云端 WWO 检出中的
`/workspace/wwo/experiments/economy_quantity_lab/` 实现并实际运行。没有接入正式游戏，
没有修改 war_resolver、FormalWorldEconomySimulation、人物、人口、GameClock、存档或 UI；
没有提交、推送、PR 或合并。检出 HEAD 为 `622b260bc641036c23efbf6345a548485ac6c475`。

## 模型与运行

`fixture.json` 保留批准的全部初值、整数配方、生产上限、目标、已知供应商、线路时延、
每日需求和冲击区间。两组使用相同初始条件；唯一差异是 shock 的第 50–79 日 A→B 新发运
容量由 100 变为 30。没有预设减产或恢复日期，没有随机数。

每日 10 machine 对应 40 steel、80 coal。正常 A/B/C 上限 100/60/15，线路上限
100 coal 与 60 steel，均容纳得下正常需求；上限不是必须生产的数量。

严格按到货、终端订单、统一状态下计算生产计划并执行、终端交付、补货、FIFO 发运、
数量检查的顺序推进。新订单当日可以发运；新产出也可以发运，但下游必须等到
`dispatch_day + lead_time` 才能使用。煤矿开采是显式物质来源，终端交付是显式边界流出。
无 reserved、损耗、付款、所有权变化、取消订单、多供应商匹配或需求预测。

订单的 pending_dispatch 与 delivered 是各生命周期阶段的账目；in_transit 从该订单
尚未到货的 shipment 推导，库存位置再从实际库存及未完成订单推导。没有独立维护一份
可与订单失配的 outstanding_inbound。每次订单事件均检查
`ordered_quantity = pending_dispatch + in_transit + delivered`。
订单本身不进入商品数量账。累计开采、生产与交付递推；每日调度只处理未到货 heap，
订单余额只查看未完成订单；完整历史只保留给输出和检查，不用于更新累计量。

实际执行的主要命令（工作目录为上述实验目录）：

```bash
PYTHONDONTWRITEBYTECODE=1 python3 run_experiment.py
PYTHONDONTWRITEBYTECODE=1 python3 -m unittest -v test_economy.py
PYTHONDONTWRITEBYTECODE=1 python3 package_experiment.py
```

打包程序从 ZIP 解压后的目录实际执行：

```bash
python3 -m unittest -v test_economy.py
python3 run_experiment.py --output-dir replay
```

子进程使用与父进程相同的 Python 解释器，并设 `PYTHONDONTWRITEBYTECODE=1`。
它比较两个逐日 CSV 和两个订单轨迹 CSV 的全部字节及 SHA-256。
本地额外的 `verification.json` 记录 ZIP 校验和、文件清单及复现校验和。

## 实际观察

所有下面的日数来自实际状态计算和 CSV 比较，表示日末状态；产量为当日生产量。

| 指标 | baseline | transport_shock |
|---|---:|---:|
| 运行天数 | 200 | 200 |
| 累计终端交付 machine | 2000 | 2000 |
| terminal_backlog 峰值 | 0 | 148（第 82 日） |
| backlog 首次出现 | 无 | 第 59 日（4） |
| 出现积压后首次清零 | 不适用 | 第 141 日；此后保持 0 |
| B 首次低于同日基线 | 不适用 | 第 55 日：20 对 40 steel |
| C 首次低于同日基线 | 不适用 | 第 59 日：6 对 10 machine |
| coal/steel/machine 每日数量残差 | 全部 0 | 全部 0 |

基线初始过渡是可解释的：第 1 日 B 不生产，先发出已有 40 steel；第 2 日 B 开始
每天生产 40；第 3 日 A 开始每天开采 80。第 4–200 日保持每天开采 80、生产
40 steel、生产并交付 10 machine，零终端积压、零等待发运的采购余额。
没有无法解释的库存增长、缺货或订单膨胀。

基线稳定日末库存为 A coal=320、B coal=160、B steel=0、C steel=80、C machine=0。
A→B 在途 160，B→C 在途 40，因此 B coal 库存位置=320，C steel 库存位置=120。
这不是初始仓内库存一直保持不变：原料目标是库存位置，包含在途。
B 的成品目标 40 用于发运前的生产计划；补货订单在生产后创建并可当日发运，所以
B 日末 steel=0，并未实现 40 的日末成品缓冲。这是固定阶段顺序与控制式共同产生的
模型特征，保留原规则，没有把目标改成另一种控制器。

冲击因果证据：第 50、51 日仍收到之前发出的 80 coal；第 52 日起收到 30。
B 日末 coal 在第 52、53、54 日从 110 降至 60、10。第 55 日开始时仅有
10+30=40 coal，配方最多支持 20 steel，故低于基线 40；不是写入日期触发减产。
C 使用自己的 steel 缓冲，第 55 日仍收到前日 40 steel；第 56 日收到 20，此后
收到 15。第 58 日末余 10 steel，第 59 日到货 15，因此最多生产
`25 // 4 = 6` machine，余 1 steel，首次产生终端积压 4。

恢复分为不同现象：

- 第 80 日新发运容量恢复 100，但煤炭到货仍为 30，B 仍生产 15，C 仍生产 4，
  终端积压为 135。A 当日生产也仍为 30，因为恢复发运发生在生产阶段之后。
- 第 82 日首次收到恢复运力发出的 100 coal，B 产量恢复并超过基线，为 50。
  第 83 日 C 首次恢复并超过基线，为 13。第 82 日仍仅生产 4 machine，
  因而 backlog 此日达到峰值 148。
- 第 83–141 日 B 每日生产 50 steel；C 在 13、12 间交替。
  正常煤炭发运上限 100、配方 2×4，使这一阶段平均可持续产出约 12.5 machine/日，
  有约 2.5/日额外产量清理积压，并非直接达到 C 最大产能 15。
- 第 141 日终端积压清零，但 B coal 仍为 0、C steel 为 0，煤炭等待发运 120，
  钢材等待发运 70；运输和原料恢复尚未完成。
- 第 142 日起 C 稳定回到 10 machine/日。钢材等待发运余额第 148 日首次回到 0，
  第 149 日 C steel 恢复基线日末 80，B 稳定回到 40 steel/日。
- 煤炭等待发运余额第 154 日首次回到 0，但仍有 200 coal 在途；第 156 日所有
  仓内库存恢复对应基线，coal 在途也回到 160，A 恢复 80/日。
  第 156 日煤炭到货仍是最后一批 100；第 157 日起当日流量与全部记录状态
  （忽略已经结束的冲击容量差异）与对应基线完全一致。

观察结束时仍有正常补货在途；“积压清零”不表示供应链不再下订单或没有在途货物。
两组最终累计值相同：开采 coal=15840、生产 steel=7960、生产与交付 machine=2000。
初始总量从 fixture 推导为 coal=720、steel=160、machine=0；终日数量账分别是
coal `320+160+160 = 720+15840-2*7960 = 640`，
steel `80+40 = 160+7960-4*2000 = 120`，machine `0+2000 = 0+2000`。
这些是分别按商品和配方定义的恒等式，不是不同商品数量相加后的物理质量守恒声明。

## 订单轨迹、检查与问题

CSV 含日末各处三种库存、当日产量、线路容量/发运/到货、pending_dispatch、in_transit、
new_order、未能采购的缺口、库存位置、终端积压/交付、累计量和逐商品残差。
每份主 CSV 有 200 行；baseline 订单轨迹 1194 行，shock 轨迹 1570 行。
轨迹包含接受、分批发运、实际到货及各事件后的完整订单余额，可按 order_id 筛选。

shock 的订单 98 是实际分批例子：第 50 日接受 80 coal；第 50/51/52 日分别发出
30/30/20，严格在第 52/53/54 日到达。第 52 日第一次到货后余额为
pending=20、in_transit=30、delivered=30；同日继续发出 20 后变为
pending=0、in_transit=50、delivered=30；第 54 日 delivered=80，其他余额=0。

8 项自动检查覆盖部分发运与 FIFO、时延与一次到货、冲击不重排已发货事件、投入不足
及整数余料、等待发运/在途不重复补货、空/错误已知供应商的采购失败记录、在途钢材不
再次触发生产、同日上游产出不能直接使用、两组全部日账、订单账、运输上限、确定性，
以及每一个已发布 CSV 单元格。发运阶段另检查仓库扣减与新增 shipment 数量一致。
没有观察到重复补货、提前到货、重复记货、负余额或数量残差。

首次测试中，部分发货测试错误地预计第二笔订单最后 10 单位在第 5 日已经到达，
实际第 4 日发出、2 日时延，应为第 6 日。修正的是测试断言；算法、fixture 和两组
CSV 未因此调整。随后 8 项通过，ZIP 解压后的同组检查与字节复现也通过。

检查通过只证明这些有限场景的实现与所列数量约束一致，不证明经济模型正确。
减产日期、12/13 的整数循环、长期日末 B steel=0、恢复日期均依赖这组固定控制规则、
缓冲初值、固定需求与时延，不能直接推广到完整 WWO。这里只验证采购候选范围限制，
没有验证多供应商匹配。没有测量或推断 WWO 全球模拟性能。
此供应链没有价格、资金、家庭与金融循环，不能称为完整经济闭环。
