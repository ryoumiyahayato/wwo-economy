`round2-full`；55 分钟总上限，每个阶段另设有时限的子进程。每次综合任务只恢复一次

阶段独立记录失败；导入失败后仍尝试有条件运行不依赖故障部分的经济检查。
不在用户 Windows 或本地启动引擎；Godot 操作只由 GitHub 托管 Linux 执行。

  基线、供应、需求、运输及组合冲击各运行365日；旧 `benchmark` 接口保持可用。

  指数判断9/改价0的历史数据比较须标注初始条件不同，不能冒称严格历史重放。
- `industry` 在原区域工厂、设备、劳动力、工资和 Formal 生产器中配置
  有限煤2+铁矿1→钢1。充足/缺煤/缺矿三组只有初始材料不同；
  核对原 StockLots 消耗、实际产出、现金和恢复一致性。不用宏观缓冲充当原料。
  第二组综合作业曾发现：下游仅配置库存目标而无自报价，原可选补货策略合法拒绝。
  保留失败记录；三组条件统一加入与本地到货成本相等的12单位开发报价，仍不保证成交。
  后续验收要求实际钢材订单和下游收货，缺任一投入时仍不得生产或交付钢材。
- `trade` 从实际空间目录寻找伦敦港—勒阿弗尔航线，配置明确开发卖方、买方、
  承运人、有限货源及2单位/日容量、2日航程。双方约定原 Formal 本币结算；
  这是显式开发合约，不声称历史英国企业使用法币，也不伪造汇兑。
  真实订单预留→运输→收货→货款和运费结算必须全部发生，重复命令不得重复扣款。
- `gen23_economy.py` 新增独立 `private.wwo.gen23-economy.v2`，要求精确候选SHA、
  已校验的覆盖层文件清单和真实引擎版本。旧v1仍检查旧固定提交，没有关闭版本保护。
  复用原人物宿主和网页 `NativeEconomyScene`，原身份、已知报价、原命令及状态差异仍来自原世界。
  最终链路通过真实 loopback HTTP bridge 创建会话、逐步推进和提交本人命令；
  修正了独立插件加载时的模块路径，并增加不启动本地引擎的加载回归测试。
- `ui` 实例化原全球地图场景及原商号，商号接入新建宿主，检查桌面和移动尺寸布局。
  不将无GPU布局检查描述为移动设备帧率或人工游戏验收。
  检查实际公开指数滞后2日、不泄露研究供需；调用实际标签筛选函数，最多4个重点加选中地区。

全球参考模型的法国样本现按原空间目录 `parent_country_id` 限定，
不会把英国卖方的库存、生产和消费误计为法国；正式货物仍由原 StockLots 拥有。

Artifact 配额已满，综合模式完全跳过 Artifact 上传，不重试。主要证据写 Actions Summary、
有限日志及 `WWO round2` check annotations。annotation 内为 zlib+base64 压缩的小型JSON，
供读取真实结果；每条小于4096字节，只发经济阶段，避免单步骤annotation数量上限。
首次成功作业的长annotation被截断，原Summary仍保留；该报告限制不作模型失败。
其中不包含原玩家存档、凭据、地图或完整工程。审阅后的少量数值和因果记录
可以提交到本仓库。各阶段PASS仅表示其明确断言成立；不自动证明完整综合闭环或历史真实性。

## 有限粮食后续选择（2026-10-25）

原 `round2-full` 保留供历史使用，本轮不选择它。

先以不可变第二轮参考源码和未改变的企业谓词重建24日新世界，再补记原30日
报价决定缺失的初价、当前价、取整目标、公告日期和逐项阻塞条件。这是开发起点的
有限重建，不是读取玩家旧存档。然后在同一个合法新快照、同样的2单位港口订单、
时间、合同和既定冲击下各推进30日；分别只关闭有限实物分区采用或目标企业的
指数采用，参考市场始终存在。企业报价、订单、交付和Ledger仍由原机制执行。

`grain` 的公斤含义是开发假设，换算为吨的系数是0.001；样本为固定原生地点，
不代表全国，权重为1。生产/耗用使用原物理累计事实的边界差值；宏观替换块是
这些地点在启用时已观察完整日的均值，明确属于开发分区假设，不是已校准的全国份额。
当前实物到货无法对应估计进口中的合同覆盖范围，因此保留真实商品、来源、目的地、
分钟与货批观察，但采用进口贡献为0，不简单叠加到估计进口。库存存量不加入日供给。
旧格式快照不补入新样本，保留旧观察，未来不重复采用其最后一天的流量。

本轮结果、运行提交与未验证范围另在研究报告的后续节记录；配置 `stale_base`
始终作为独立的配置持久化问题，未确认解决前不得由经济运行结果替它销项。

### 粮食报价归因后续（预先声明的唯一情景）

继续使用同一 `grain-followup` 手动选择，当前阶段不再重跑 `coupled-reasons` 或上轮
三个实物流量条件。旧脚本函数和结果保留；本阶段只做一次资源恢复、一个经营情景的
公告采用/目标企业忽略公告两个条件，各预热24日后从同一快照观察30日。

经营情景基于原 `Consumer.configuration("consumer_combined")`，只将里昂上游的grain
成品缓冲目标从8设为0。原上游开仓grain仍为8、开局价格3、企业现金220、生产grain
每批2、规划期4日及既有买方的需求和采购规则保留。0表示不额外持有这8单位成品缓冲；
实际产量仍取决于原已接订单、请求、劳动和产能，不是暂停生产。所有资金和实物初始
资产总量保持原Consumer开局，两个条件间相同。本阶段不重演伦敦港合同，不拿其原价
交付替代目标企业的新报价证明。共同运输设置由原合法命令完成，之后采购、生产、
交付和消费均自主运行，不由脚本买入、删库存、补现金或发布价格。

原生产计划以 `target + urgent + ceil(recent_orders/window)*planning_horizon` 为目标，
再扣已有与在途敞口。原8单位缓冲与向上取整订单覆盖相加，使库存高于指数采用上限6；
不把它认定为bug。在近期每3日约1至2单位订单、取整日均1时，取消额外缓冲使订单覆盖
约为4单位；每批2的补充可能带来余量，故4至6范围有机会与近期实际交付同时出现。
实际是否到达由本次记录决定，不在运行后反复调参。

报价谓词提取为唯一 `quotation_step`，原NPC和脱离交易世界的归因计算共同调用。
真实有效已接收指数与中性数值100使用同一现价、库存、销量、现金拒绝及规则；中性值
不是公告，不发给企业，也不提交到交易世界。分别记录自身规则、锚定回升和指数数值
差异。不同目标若位于现价同侧，单次tick结果也可相同；目标相同更不能证明指数涨幅
影响了价格。旧10次决定由已有结果直接读取后计算归因，不重新模拟旧情景。

原恢复、锁价、重复已接受命令及原Ledger付款ID检查保留。0.001换算、权重1、未知
进口覆盖和原参考市场均不改；不建立其他情景、门禁、矩阵或独立脚本。
